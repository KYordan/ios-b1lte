# GPU G0: decisions (2026-11-04)

## 1. Does iOS 26's CoreAnimation still have a GLES renderer? **Yes.**

Analysis of `QuartzCore` extracted from the 23G90 cache (`dsc_extractor`, `llvm-nm`):
- `CA::OGL::GLESContext`: ~45 real methods (`GLESContext(void*)`, `init_state`, `set_surface`, `bind_image_impl`,
  `create_surface_from_iosurface`, `make_buffer_current(CA::WindowServer::Surface*)`, `release_display_surface`,
  `warmup_shaders`, `copy_destination`, `bind_gaussian`…), plus `GLContext` (54) and `GLESImage`.
- The two other engines: `MetalContext` (306 symbols) and `SWContext` (the current software rendering, 37 + 379 `SW`).
- `+[CARenderer rendererWithEAGLContext:options:]` and `CAEAGLLayer` complete; `OpenGLES.framework` present
  (`GLEngine.bundle`, `libGLImage`, `libGLProgrammability`, 44 `EAGLContext` symbols).

`make_buffer_current(WindowServer::Surface*)` shows that the GLES context can draw the display server's surfaces, not only isolated layers. **Decision: the EAGL path (S7 method, Mesa/Panfrost) is the main path.** Metal → Vulkan remains a secondary investigation.

`CA*` preferences), by signature search, without any hard-coded address.

## 3. Hardware facts (S10 DTB)

| Element | Value |
| --- | --- |
| GPU | `mali@18500000`, `compatible = "arm,mali"` |
| Power domain | `pd-embedded_g3d@15862100` (reg 0x20), `cal_id 0xb1380007`, **`need_smc = 0x18410204`** |
| Power state | `gpu_pmu_status_reg_offset 0x2104` (PMU 0x15860000), mask `0x1` |
| Clock (CAL) | `g3d_cmu_cal_id 0x0b04000a` (GPU DVFS via ACPM, like the CPUs) |
| Frequencies | `gpu_max_clock 702000`, `gpu_min_clock 156000`, startup `260000` kHz; DVFS table (9 × 8) |
| Default voltage | `gpu_default_voltage 800000` µV |
| Thermal | TMU sensor `G3D@100A0000`; thresholds 95 / 105 / 115 °C |

G1 (B1L-0014): read-only of the power state; `GPU_ID` read only if the domain is already powered.
Power-on (SMC + CAL) comes afterwards, with the exact Samsung sequence.
